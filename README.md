The paper uses release `v0.5.5` of the code, benchmark spec, and datasets.

BabyTheorist is a visual benchmark for **Learning to Theorize the World from Observation**. A
model observes many before/after pairs `(x, y)`: something changes between the
two grids, but the cause of that change is never given. From these observations
alone, the model must form reusable theories of how changes happen, use those
theories to explain new phenomena, and extend them to increasingly complex
compositions. The benchmark tests theory-building from observed change, not
program supervision or instance-specific input-output memorization.

## Learning Objective

BabyTheorist follows the observation-to-theory setting:

- A phenomenon is a before/after observation pair `(x, y)`.
- The learner observes that a change occurred, but not what mechanism caused it.
- Across many such observations, the learner should discover reusable primitive
  changes and learn how they compose.
- Each pair is generated by an underlying latent program, but that
  program is not part of the training signal.
- A good model should turn observations into executable theories, reuse those
  theories to explain new inputs, and generalize to more complex compositions
  than those seen during training.

This differs from standard few-shot reasoning tasks. BabyTheorist is primarily about
learning reusable primitives and compositional program induction from many
ungrouped observations. Evaluation then measures whether an inferred theory
transfers.

## Benchmark Shape

BabyTheorist tasks are generated from:

- A square grid with colors `0..9`, where `0` is background.
- A scene of independent shapes with fixed object identities.
- A latent program, represented internally as a list of
  `Step(selector, primitive, target?)`.

Benchmark generation defaults:

- Levels: `1..8`
- Depth: sampled from the official piecewise-geometric prior centered at `L+1`
- Train split: one pair per task, `P=1`
- Eval split: adaptive support set plus one query, capped at `K<=5` by default
- Full release size: `250,000` train tasks and `10,000` eval tasks per level
- Default scene config: `15x15`, shape size range `4..16`
- Default backend: `filter`

Benchmark mode controls the program language and default object count:

- `multi_dev`: two objects, `by_index` selectors only, translate primitives
  only (`translate_up/down/left/right`). Development suite only: it is not used
  in the paper and is not part of the dataset release.
- `single-A` / `single_a`: one object, `by_index` selectors only, single base
  primitives.
- `multi-A` / `multi_a`: two objects, `by_index` selectors only, multi base
  primitives including relational base operations.
- `single-B` / `single_b`: one object, `by_index` selectors only, staged primitive
  unlocks.
- `multi-B` / `multi_b`: three objects, hard selector set, staged primitive
  unlocks.

The train split is the observation-only learning corpus: each row is one
phenomenon `(x, y)`. The eval split is a transfer probe: the model sees a
support set of observed phenomena, infers a theory, and must apply it to a
query input. Eval support is sampled adaptively until the query answer is
unique under the benchmark's selector ambiguity model, or the task is rejected
at the configured support cap.

Level `L` is a distribution over task depths, not a single depth. The official
prior is centered at `c=L+1`, assigns 80% probability to `d<=c`, 15% to the
near-harder shoulder `c+1,c+2`, and 5% to a geometrically decaying hard tail
beyond `c+2`. Generation truncates this tail after six hard-tail depths, so
level `L` samples from support `1..L+9`.

Important CLI options:

- `--level`: curriculum level id `L`; task depth is sampled from the official
  piecewise-geometric prior centered at `L+1`.
- `--shape-profile standard`: default random-walk shape profile with
  pixel-budget range `4..16`, random-walk compactness `8`, and bordered/hollow
  minimum target size `9`; bordered/hollow objects use the randomized inner
  walk sizing, with sampled object bounding-box span capped at `5` to remove
  elongated outliers. Individual flags `--shape-min`, `--shape-max`,
  `--shape-compactness`, and `--shape-border-min` override the profile
  defaults; `--shape-max-bbox-span 0` disables the bounding-box cap.
- `--benchmark-mode multi_dev`: two-object development suite with only
  `translate_up`, `translate_down`, `translate_left`, and `translate_right`.
  Not used in the paper and not part of the dataset release.
- `--benchmark-mode single-A` / `single_a`: one-object A suite.
- `--benchmark-mode multi-A` / `multi_a`: two-object A suite.
- `--benchmark-mode single-B` / `single_b`: one-object B suite.
- `--benchmark-mode multi-B` / `multi_b`: three-object B suite.
  Legacy names `single_easy`, `multi_easy`, `single_hard`, and `multi_hard`
  are accepted as aliases and normalized to the A/B labels.
- `--primitives`: comma-separated primitive vocabulary; overrides the preset.
- `--selectors`: comma-separated selector vocabulary; overrides the preset.
- `--backend filter`: default constraint-forward generator.
- `--backend rejection`: legacy rejection sampler, kept for comparison.
- filter metadata: the production filter writes `filter_system`,
  `filter_rules_version`, and `filter_grounding_version` to generated sidecars.
- `--dominant-pool-dir` / `--frequent-subprogram-pool-dir`: directory for
  reusable abstract frequent-subprogram pool caches. Suite scripts default this to
  `data/dominant_pools-v<babytheorist_version>` so repeated level/split generation
  and worker processes do not rebuild the same frequent-subprogram pools.
  The `dominant_*` metadata keys and `dominant_pools` directory name are
  retained as legacy compatibility names.
  Official caches also record `dominant_viability`: abstract entries are kept
  only after concrete grounding and a lightweight pair-generation preflight
  under the current task shape/world configuration.
- `--mode train`: one `(x, y)` pair per task.
- `--mode eval`: support/query task with singleton `valid_query_outputs` by default.
- `--min-support`: eval support floor for adaptive unique-support generation
  (default 2).
- `--max-support`: eval support cap for adaptive unique-support generation.
- `--allow-ambiguous-eval`: legacy K=1 eval mode where non-singleton `Y_q` is accepted.
- `--workers`: multiprocessing workers; fixed seed remains reproducible.

## Benchmark Suites and Frequent-Subprogram Library

Official benchmark modes fix the default object count, selector set, and
primitive curriculum. `--n-shapes` and `GenerationConfig(n_shapes=...)` still
override the object count for custom experiments.

| suite mode | objects | selectors | primitive curriculum |
| --- | ---: | --- | --- |
| `multi_dev` (development only) | 2 | `by_index` | translate only |
| `single-A` / `single_a` | 1 | `by_index` | single base only |
| `multi-A` / `multi_a` | 2 | `by_index` | multi base only |
| `single-B` / `single_b` | 1 | `by_index` | single base plus unlocks |
| `multi-B` / `multi_b` | 3 | hard selector set | multi base plus unlocks |

The `multi_dev` vocabulary is only `translate_up`, `translate_down`,
`translate_left`, and `translate_right`. The single base vocabulary is `rot90`,
`flip_h`, `flip_v`, `next_color`, `translate_up`, `translate_down`,
`translate_left`, and `translate_right`.
The multi base vocabulary adds `swap_colors`, `align_row`, and `align_col`.
A suites keep this base vocabulary for every level.

B suites use an append-only primitive curriculum:

| levels | newly introduced primitive | effective hard vocabulary |
| --- | --- | --- |
| `L1` | none | base |
| `L2-L3` | `hollow` | base + `hollow` |
| `L4-L5` | `fill_interior` | base + `hollow` + `fill_interior` |
| `L6-L7` | `add_border` | base + `hollow` + `fill_interior` + `add_border` |
| `L8+` | none | base + all unlocks |

The hard frequent-subprogram library mirrors that curriculum. Generation first builds a
validated `base` abstract frequent-subprogram pool from the L1 base vocabulary. Each
unlock appends a new segment, for example `append:hollow`,
`append:fill_interior`, then `append:add_border`. An append entry must contain
the newly introduced primitive exactly once; its prefix and suffix are composed
from the inherited library available before that unlock, and the full abstract
program is admitted only after the normal filter validation and frequent-subprogram
viability preflight pass. The preflight grounds the selector-free abstract
program to concrete selectors and, for official generation configs, verifies
that at least one lightweight `(x, y)` pair can be generated.

During an unlock window, hard sampling uses the current-intro segment 50% of
the time and the inherited library the other 50%. The inherited library is
cumulative: at `L6-L7`, `add_border` is introduced on top of `base`,
`append:hollow`, and `append:fill_interior`. `fill_interior` has one targeted
precondition: the affected input slot is generated as hollow so the primitive is
valid. The generator does not force a `hollow -> fill_interior` round trip into
the same program.

Filter rules also add local bbox-safety input constraints for bbox-changing
primitives such as `rot90` and `add_border`. Movement and pixel collision
failures remain engine-level checks because forcing them into the scene
constraint system over-constrains deep programs and slows generation.

Frequent-subprogram pools are cached under `--dominant-pool-dir` or
`--frequent-subprogram-pool-dir`. Direct abstract pools are
capped at depth 10; deeper sampled depths are generated by composing cached
chunks rather than rebuilding a direct entry for every depth. The default suite
frequent-subprogram library budget keeps 20 base entries per depth; hard-suite unlock
segments keep 10 current-intro append entries per depth.

## Primitive and Selector Vocabulary

Primitives are defined in `babytheorist/primitives.py`.

Transform primitives:

- `rot90`
- `flip_h`
- `flip_v`
- `next_color`
- `fill_interior`
- `hollow`
- `add_border`

Movement primitives:

- `translate_up`
- `translate_down`
- `translate_left`
- `translate_right`

Relational primitives:

- `swap_colors`
- `align_row`
- `align_col`

The suite vocabularies are defined by the benchmark curriculum above.
`multi_dev` uses only the four translate primitives, `single-A` uses the
single base vocabulary, `multi-A` adds the relational base primitives, and
B suites append `hollow`, `fill_interior`, and `add_border` only at their
unlock levels.

Selectors are defined in `babytheorist/core.py` and resolved in `babytheorist/selectors.py`.

Multi-select selectors:

- `ALL`
- `by_color(c)`
- `is_hollow`

Single-select selectors:

- `by_index(k)`
- `topmost`
- `bottommost`
- `leftmost`
- `rightmost`

`multi_dev`, A suites, and `single-B` use only `by_index(k)`. `multi-B` uses every
selector listed above.

`by_index(k)` is 1-based. When `by_index` is enabled, scenes are sorted by
input raster position before execution, and the index refers to object identity
throughout the program.

## HDF5 Format

`babytheorist/review.py` writes HDF5 exports. `env/io_h5.py` is the single reader used
by the benchmark environment.

Each HDF5 file contains:

```text
inputs                 (N, P, H, W) int8
outputs                (N, P, H, W) int8
grid_sizes             (N, 2)       int32
n_shapes               (N, P)       int32
depths                 (N,)         int32
transformation_suites  (N,)         JSON string per program
valid_query_outputs    (N,)         JSON string, eval only
n_support              (N,)         int32, eval only when K can vary
```

For train files, `P=1`.

`depths` and `transformation_suites` are included for analysis, auditing, and
optional diagnostics. They should not be used as training supervision when
evaluating observation-only theory induction.

For eval files, generated data uses adaptive support:

- slots `[0, K)`: support input/output pairs
- slot `K`: query input and canonical query output
- `n_support[i]`: the row's value of `K`
- `valid_query_outputs[i]`: singleton query output set after the support set
  has removed selector ambiguity for that query

The default benchmark generation uses `2 <= K <= 5`: every eval row has at
least two support observations, and generation adds more up to five only when
needed to make `valid_query_outputs[i]` singleton.

Evaluation accepts a prediction if it matches any grid in `Y_q`; in the default
unique-support benchmark, `Y_q` has length 1. Legacy ambiguous eval files with
larger `Y_q` remain readable and scoreable.

## Benchmark API

Use `BabyTheoristEnv` for static train/eval access. The basic training examples expose
only observations:

```python
from env import BabyTheoristEnv

env = BabyTheoristEnv(data_dir="data", levels=(1, 2, 3), mode="single-A")

train = env.train(level=1, n=250_000)
example = train[0]
print(example.x.shape, example.y.shape, example.task_id)

for batch in train.iter_batches(batch_size=4096):
    print(batch.x.shape, batch.y.shape, batch.task_id.shape)

eval_set = env.eval(level=1)
row = eval_set[0]
print(row.support_x.shape, row.support_y.shape, row.query_x.shape)
```

When `mode` is set, `data_dir` is treated as a root directory and the
environment reads from the versioned mode directory, for example
`data/single_a-v0.5.5`,
`data/multi_a-v0.5.5`, `data/single_b-v0.5.5`, or
`data/multi_b-v0.5.5`.
If any required HDF5 file is missing, `BabyTheoristEnv` generates only the missing
files with the official preset for that mode. Existing files are reused. To
inspect an already materialized directory directly, omit `mode` and pass the
exact directory containing `lv{level}_{split}.h5`.

Legacy descriptive modes resolve to public A/B directories. For example:

```python
env = BabyTheoristEnv(data_dir="data", levels=(1,), mode="single-A")
print(env.mode)      # single_a
print(env.data_dir)  # data/single_a-v0.5.5
```

This means `mode="single-A"` requires `data/single_a-v0.5.5/` when
`generate_missing=False`; it will not silently fall back to
`data/single_easy-v0.5.5/`. If auto-generation is enabled, it writes
`data/single_a-v0.5.5/` and records the public `single_a` mode. Existing
sidecars that still record legacy `single_easy` are accepted for compatibility.

For a smaller local run:

```python
from env import GenerationConfig, BabyTheoristEnv

env = BabyTheoristEnv(
    data_dir="data",
    levels=(1,),
    mode="single-A",
    generation=GenerationConfig(train_n=1000, eval_n=100, workers=4),
)
```

Score a model function:

```python
def model_fn(support_x, support_y, query_x):
    return query_x

report = env.score(model_fn, level=1)
print(report.accuracy)
```

Or submit explicit predictions:

```python
preds = [(ex.task_id, model_fn(ex.support_x, ex.support_y, ex.query_x))
         for ex in env.eval(level=1)]
report = env.score_predictions(preds, level=1)
```

Use `BabyTheoristGym` for the benchmark loop. The environment decides whether
the next interaction is train or test; the model consumes the returned data and
submits predictions only during test phases.

```python
from env import BabyTheoristGym

gym = BabyTheoristGym(mode="multi-A", data_dir="data")

while gym.active:
    data, phase = gym.interact()

    if phase == "train":
        observations = data
        model.fit(observations)

    elif phase == "test":
        eval_tasks = data
        predictions = model.predict(eval_tasks)
        report = gym.submit(predictions)
        print(
            report.level,
            report.eval_submissions,
            report.n_exposed,
            report.accuracy,
            report.passed,
            report.cumulative_score,
        )

print(gym.result())
```

With `mode="multi-A"`, `BabyTheoristGym` reads from `data/multi_a-v0.5.5`
while exposing `gym.mode == "multi_a"`. `mode="multi_easy"` remains accepted
as a legacy alias and resolves to the same path.
If the required files are missing, `BabyTheoristEnv` automatically generates them with
the matching `generate.py --benchmark-mode` suite preset, including the
primitive curriculum and append-only frequent-subprogram library. The supported
public suite names are `single-A`, `multi-A`, `single-B`, and `multi-B`, plus
their underscore/lowercase variants. `multi_dev` is also accepted as a
development suite.
Auto-generation stores reusable depth-10 frequent-subprogram library caches next to the
mode directory, e.g. `data/dominant_pools-v0.5.5`, unless
`GenerationConfig(dominant_pool_dir=...)` overrides it.
`GenerationConfig` defaults to `seed=42` and `pool_seed=42`; set both
explicitly when you want `BabyTheoristGym` auto-generation to reproduce a specific
dataset and frequent-subprogram library.
It also supports the same shape profile as `generate.py`. The default
`GenerationConfig()` auto-generates the official `standard` shape distribution.
Existing files with mismatched `shape_generation` metadata are rejected instead
of being silently mixed.

For a small smoke run that auto-generates tiny files instead of the full
default benchmark size:

```python
from env import GenerationConfig, BabyTheoristGym

gym = BabyTheoristGym(
    mode="multi-A",
    data_dir="data",
    generation=GenerationConfig(
        train_n=100,
        eval_n=20,
        workers=4,
        seed=42,
        pool_seed=42,
    ),
)
```

Existing files with a non-official recorded `depth_distribution` are rejected
instead of being silently mixed with the current benchmark data.

During `train`, `data` is the current level's independent `(x, y)` training
split; official suite files contain 250K rows per level, while local smoke
configs may be smaller. During `test`, `data` is the current level eval set;
each example exposes `task_id`, `support_x`, `support_y`, and `query_x`.
`model.predict(data)` should return explicit predictions as `(task_id, grid)`
pairs.

For training throughput, prefer `train_data.iter_batches(...)` or
`train_data.as_arrays()` over manually stacking row examples. The official
loading guidance and benchmark script are in `docs/data_loading.md` and
`scripts/bench_data_loader.py`.
Newly generated HDF5 files store `inputs` and `outputs` as contiguous
uncompressed datasets. Older files with chunked or compressed `inputs` /
`outputs` should be regenerated or rewritten before high-throughput training.

Recommended training loader pattern:

```python
for batch in train_data.iter_batches(batch_size=4096):
    model.update_batch(batch.x, batch.y, task_id=batch.task_id)
```

For PyTorch-style pipelines, wrap BabyTheorist's batch iterator instead of wrapping
`train_data` directly with `DataLoader(..., batch_size=...)`; the latter falls
back to one HDF5 row read per sample.

```python
import torch
from torch.utils.data import DataLoader, IterableDataset


class BabyTheoristTrainIterable(IterableDataset):
    def __init__(self, train_data, batch_size=4096, start=0):
        self.train_data = train_data
        self.batch_size = batch_size
        self.start = start

    def __iter__(self):
        for batch in self.train_data.iter_batches(
            batch_size=self.batch_size,
            start=self.start,
        ):
            yield {
                "x": torch.from_numpy(batch.x).long(),
                "y": torch.from_numpy(batch.y).long(),
                "task_id": torch.from_numpy(batch.task_id),
            }


loader = DataLoader(BabyTheoristTrainIterable(train_data), batch_size=None)

for batch in loader:
    model.update_batch(batch["x"], batch["y"], task_id=batch["task_id"])
```

When using `BabyTheoristGym`, each level starts with a zero-observation test. If that
fails, the gym exposes one train payload for that level. A stateful model can
process that payload once:

```python
if phase == "train":
    for batch in train_data.iter_batches(batch_size=4096):
        model.update_batch(batch.x, batch.y)
```

`BabyTheoristGym` always starts at level 1 and increases levels until the model fails.
Each level starts with a zero-observation entry test. If that fails, the model
gets one train split, followed by one charged same-level eval submission. The
default maximum is one charged eval submission per level, excluding the entry test; set
`BabyTheoristGym(..., max_eval_submissions_per_level=...)` for local experiments. The
pass threshold is fixed at `0.80`.

## Benchmark Scoring

The primary metric is `score`, reported on `gym.result().score`. Each eval
accuracy is converted to points with `accuracy * 100`, so a level eval at
`0.92` is worth `92.0` points. For each level, BabyTheorist keeps the best eval score
observed at that level, including the zero-observation entry test. The final
score is the sum of those per-level best scores, including the failed terminal
level.

`GymReport` exposes both the current eval score and the running benchmark
score:

- `report.score`: this eval's score in points.
- `report.level_best_score`: best score seen so far for this level.
- `report.cumulative_score`: sum of current best scores across reached levels.
- `report.entry_eval`: whether this was the free level-entry test.
- `report.eval_submissions`: charged eval submissions used in the current
  level, excluding entry tests.
- `report.charged_eval_trials`: total charged eval submissions across the run.

The secondary metric is `efficiency`, reported on `gym.result().efficiency`.
It is normalized AUC over the eight-level curriculum:

```text
efficiency = score_auc / (100 + 200 + ... + 800)
```

The AUC uses the cumulative score after each official level and extends the
curve flat after the learner stops. The denominator is the maximum achievable
eight-level area: a perfect learner's cumulative score curve. If the AUC is zero,
`efficiency` is `0.0`. Ranking should use `score` as the primary metric and
`efficiency` as the secondary metric.

## Filter Backend

The default generator is not a brute-force BFS generator. It is a
constraint-forward symbolic filter:

1. Sample one candidate step.
2. Apply it to symbolic per-shape state.
3. Reject the prefix if program-level rules find a shortcut.
4. Accumulate input constraints required for the prefix to remain valid.
5. Sample concrete shapes and placements satisfying those constraints.
6. Run the real engine as the final execution check.

The default filter stack lives in:

```text
babytheorist/filter/sampler.py        program + constraint sampling
babytheorist/filter/state.py          symbolic state history
babytheorist/filter/rules_program.py  program-level shortcut rules
babytheorist/filter/rules_input.py    input-level scene constraints
babytheorist/filter/constraint.py     constraint data model
babytheorist/filter/scene_sampler.py  constraint-aware scene realization
babytheorist/filter/oracle.py         brute-force oracle for verification only
```

The production filter implementation lives under `babytheorist/filter/`. It uses
meaning-based rule names and samples from prefix-valid candidate sets to reduce
repeated rejected draws. Dominant
abstract grounding is split into `babytheorist/filter/grounding.py`, which records
its version as `filter_grounding_version` metadata. The generator retries scene
realization for a grounded program before discarding the program; the retry cap
is recorded in `filter_generation_stats` as `pair_execution_retries`. Pair
execution failures are reported with structured engine subreasons such as
`engine_collision_or_oob`, `engine_noop`, and `engine_selector_empty`.

For local timing probes, run:

```bash
PYTHONDONTWRITEBYTECODE=1 python scripts/bench_filter_system.py \
  --benchmark-mode multi-B \
  --fixed-depth 5 \
  --n 100 \
  --warmups 1 \
  --repeats 3 \
  --jsonl-out docs/filter_benchmark_YYYY-MM-DD.jsonl
```

The benchmark script prints JSON records with wall-clock throughput,
generation statistics, and the exact run config. Detailed sampler
reject/candidate stats are currently most informative for single-worker runs.
Use warmups when measuring cold dominant-pool cache effects.

The production path avoids enumerating all shorter programs `Q`. Oracle/BFS
checks are used in tests and analysis to validate the rule stack, not in normal
dataset generation.

For the Learning-to-Theorize benchmark, this filtering matters because a
shortcut-corrupted depth label weakens the intended pressure toward primitive
decomposition. If a depth-5 program behaves like a depth-2 program on the actual
scene, a model can succeed by learning entangled shortcuts rather than a
reusable compositional theory.

## Reproducibility

Generation uses NumPy RNG seeds. With the same CLI arguments, seed, and worker
count semantics, outputs are deterministic. The parallel path draws per-task
seeds deterministically and preserves submission order.

Recommended benchmark seeds:

- train: `--seed 42`
- eval: `--seed 43`
- frequent-subprogram/rejection pool seed: `--pool-seed 42`

## Versioning

`v0.5.5` is the release used for all results in the NeurIPS 2026 paper. Its
code, benchmark spec, and dataset releases share the same version string.

BabyTheorist uses semantic versioning:

- `0.5.y` where `y > 5`: fixes that do not change benchmark semantics or
  invalidate reported results.
- `0.y.0` where `y > 5`: backward-compatible additions or intentional changes to
  benchmark semantics, scoring, or official data-generation policy. Such
  releases are not comparable with the paper results.

There are three related version identifiers:

- Code version: the repository/package implementation version, tagged in git
  as `v0.5.5`.
- Benchmark spec version: the semantic contract of primitives, selectors,
  generation rules, eval ambiguity handling, and scoring.
- Dataset release version: a concrete generated dataset bundle, including mode,
  seeds, backend, vocabulary, depth policy, support policy, and generator
  version.

Generated HDF5 sidecar files and JSON outputs automatically record these
identifiers as `babytheorist_version`, `benchmark_spec_version`, and
`dataset_release_version`. Suite scripts use names such as
`BabyTheorist-single_a-v0.5.5`,
`BabyTheorist-multi_a-v0.5.5`, `BabyTheorist-single_b-v0.5.5`, and
`BabyTheorist-multi_b-v0.5.5`.
Custom runs without `--benchmark-mode` use
`BabyTheorist-custom-v0.5.5`. Override the dataset release name with
`--dataset-version` when preparing a named dataset bundle.

Legacy descriptive names do not create separate dataset-release identities.
Older local PARC-era files may record `parc_version`, `PARC-...` release
names, or metadata modes such as `single_easy`; treat those as provenance
fields. The loader normalizes those legacy modes when the files live under the
matching public directory.

To reproduce the paper, use git tag `v0.5.5` and the dataset releases
`BabyTheorist-single_a-v0.5.5`, `BabyTheorist-multi_a-v0.5.5`,
`BabyTheorist-single_b-v0.5.5`, and `BabyTheorist-multi_b-v0.5.5` from
[Hugging Face](https://huggingface.co/datasets/ahn-ml/babytheorist) or the
[Dataverse record](https://doi.org/10.7910/DVN/H9UGTL).

## Current Scope

The main benchmark configurations are the four versioned suites used in the
paper: `single-A`, `multi-A`, `single-B`, and `multi-B`. The underscore
forms `single_a`, `multi_a`, `single_b`, and `multi_b` are the normalized
labels used in paths and metadata. `single_easy`, `multi_easy`,
`single_hard`, and `multi_hard` are legacy aliases.
`multi_dev` is a translate-only development suite; it is not used in the
paper and is not part of the dataset release. A suites and
`single-B` use `by_index` selectors only. `multi-B` uses the hard
selector set. B suites use staged primitive unlocks and the append-only
abstract frequent-subprogram library. The filter code also supports custom selector and primitive experiments, but custom
vocabularies should be treated as active research/development surfaces unless
they are packaged as a named benchmark suite.

The intended benchmark protocol is:

- Train on independent `(x, y)` observations.
- Do not train on ground-truth programs.
- Evaluate self-explanation by reconstructing `y` from `(x, y)` through an
  inferred latent program.
- Evaluate transfer by applying that inferred program to the eval query input.
- Follow the continual train-test protocol over the eight official levels.
  Each level begins with an entry evaluation; a learner that reaches 80%
  accuracy skips that level's training observations (level skipping).
  Otherwise it trains on the level's 250,000 observations and then takes the
  level evaluation, advancing at 80% accuracy. Skipping a level tests length
  generalization to more complex programs using theories acquired earlier.

Known development directions are tracked in:

- `docs/abstract_dominant_programs.md`
- `docs/filter_rulebook.md`

Key future work:

- Improve constructive scene realization for heavily constrained full-vocab
  programs.
- Broaden high-throughput benchmark validation for dynamic selectors.
- Continue tightening filter-aware abstract dominant programs over latent
  object slots.
